# NIGHTJAR: 512KB ROM extension

## Mapper & build facts (verified)
- Metal Gear MSX uses the **Konami mapper (Konami4, no SCC)**: **8KB segments**
  selected by writing the segment number to **`#6000`** (window `#6000-#7FFF`) and
  **`#8000`** (window `#8000-#9FFF`); the engine tracks the live segments in
  `BankIn60` / `BankIn80`. The register is 8-bit and the hardware **masks it to the
  ROM size**, so a larger ROM just needs the extra segments to exist.
- Stock ROM = **128KB = 16 × 8KB segments** (banks `0`–`Fh`). The build
  (`MetalGear.asm`) is the sequential concatenation of the bank include files,
  each of which `org`s into the page-1/2 window and ends with
  `ds (#C000-$),#ff` + `ASSERT $=#C000`:
  - `Banks0123.asm` `org #4000` → fills to `#C000` = 32KB = segments 0–3
  - `Banks456/789/ABC/DEF.asm` `org #6000` → 24KB each = segments 4–6, 7–9, A–C, D–F
- Tile graphics (`GfxBuilding`, …) live in the high banks; `SetBanks_D_E_F` maps
  segments D/E/F into the windows before the tile loader decodes them.

## Sizing — ADAPTIVE (current approach, replaces the old static reserve)
The ROM size is **emergent from real content**, snapped up to the smallest
Konami-legal power-of-2: **content ≤128KB → 128KB, ≤256KB → 256KB, ≤512KB →
512KB (hard MAX)**. We never reserve space we don't use, so stock content stays
**128KB byte-identical**; the ROM only grows when high-segment data (e.g.
extended graphics in seg `10h+`) actually pushes past a tier.

Implemented in **`tools/build.py`** (the canonical build): runs sjasm, checks
for 0 errors, then pads `MetalGear.rom` with `0xFF` up to the target tier.
- `python tools/build.py` → build + adaptive pad + report (content KB, segments
  used, chosen ROM size). `--max 256` caps the MAX.
- Importable `pad_rom(path)` / `build()`; the editor's Build button calls the
  same `build()` so CLI and editor agree.
- The old `BanksReserved.asm` (`REPT 48` of `#ff` that *always* forced 512KB) is
  **gone** — adaptive padding subsumes it. No ASM reserve block is needed; just
  include whatever bank files have real data.

**Why power-of-2 only:** the Konami4 mapper masks the 8-bit segment number
written to `#6000`/`#8000`/`#A000` down to the ROM size; that mask is only
coherent on a power-of-2 ROM, so a 140KB ROM must round up to 256KB.

**The "ROM > 256KB" warning:** a *conservative emulator heuristic* (largest
commercial Konami4 carts were ≤256KB), not a hardware limit. An 8-bit segment
register over 8KB segments addresses up to 2MB; **512KB is fully supported and
verified to run in openMSX**. Adaptive sizing means we only cross into 512KB
(and possibly trip the warning) when the art genuinely needs it.

Verified: stock build **0 errors, 131072 bytes, md5 unchanged**; tier logic
unit-tested (130KB→256KB, 257KB→512KB, 513KB→overflow error).

## Extended tilesets are now OPTIONAL (flag-gated)
`BanksExtGfx.asm` is included only when **`EXTGFX equ 1`** in `MetalGear.asm`
(next to `JAPANESE`). `EXTGFX 0` (default) = stock **128KB byte-identical**; the
ext bank, the `ExtDivert` hook in `Banks0123.asm`, and the LoadRoomTiles call-site
swap are all wrapped in `IF (EXTGFX) … ELSE … ENDIF`. `EXTGFX 1` pulls in the ext
bank (segs 10h-12h) and the adaptive sizer (`tools/build.py`) auto-grows the ROM
to **256KB**.

**Map editor toggle:** the Build·Run dashboard has an **"Extended banks"**
checkbox (`GET/POST /api/extgfx`) that flips the `EXTGFX` flag; build to apply.
The tileset dropdown only offers ids 8+ when the flag is on, and `set_tileset`
refuses to assign 8-15 unless it's on — so you can't wire a room to a tileset the
ROM won't contain. So: a user who only re-skins the original tiles leaves it off
(128KB); a user who wants NEW tiles turns it on (256KB).

## Extended tilesets are MULTI-BANK (content-driven), 2026-06-24
`BanksExtGfx.asm` (generated by `tools/genextgfx.py [--tilesets N]`) now uses a
**control segment (10h)** — always mapped to `#6000` by `ExtDivert` — holding
`idxTileSetsExt`, every `TileSetExt` config, a **`SegBaseExt`** table, every
`IdxColisTilesExt`/`CollTilesExt`, and `LoadExtDispatch`. **Each ext tileset gets
its own gfx segment** (11h, 12h, …); the dispatcher reads `SegBaseExt[id-8]` and
maps that segment into `#8000/#A000` (updating the `BankIn80/A0` shadows) before
decoding. So each tileset has a full ~8KB / 256-tile budget instead of all of
them sharing one 24KB window. **`ExtDivert` in `Banks0123.asm` is unchanged** (it
still maps base 10h and rets into `LoadExtDispatch`). The ROM grows one segment
per tileset; the adaptive sizer picks the tier. Verified in openMSX: a room on
**tileset 9** (gfx in the *second* gfx segment, 12h) renders correct Building art
— proving per-tileset remapping. mgrender/editor are label-based, no changes.

### ⚠️ Ext tilesets cap at the 256KB tier (engine data-format limit)
`RoomGfxSetIds` is a **nibble** → only **16 tileset ids total (8-15 for ext = 8)**,
and each tileset is **≤256 tiles ≈ ≤8KB** (≤3 config blocks into byte-addressed
VRAM). So 8 ext tilesets ≈ 8×8KB + 8KB control ≈ 72KB → ~200KB total → **256KB
tier, never 512KB.** Reaching the 512KB tier needs a *different* consumer for
segments 20h-3Fh (a byte-wide tileset id for >16 tilesets, or sprite/sound/
cutscene banks). **Decision 2026-06-24: ship multi-bank now (256KB tier); defer
the 512KB consumer** until there's concrete data to put there. The sizer already
supports 512KB and will auto-select it the moment such content exists.

## Phase B — using the new space for art (not yet done)
To add a NEW graphics tileset in a reserved segment:
1. **Place the data.** Convert one reserved segment into a real bank file, e.g.
   `BanksGfx16.asm` (`org #6000` … new gfx `db`/data … `ds (#8000-$),#ff`), and
   reduce the `REPT 48` count by one so the total stays 512KB. The segment number
   is its ROM offset / 8192 (first reserved = 16/`10h`).
2. **Bank it in to decode.** The tile loader currently maps D/E/F
   (`SetBanks_D_E_F`). A new tileset's gfx in segment ≥10h must be mapped before
   decoding — write the segment to `#6000` (and set `BankIn60`) the way
   `SetSoundEntry` does, decode, then restore. So a new `TileSet*` needs to carry
   its **source segment**, and `Load3bppTiles`/`LoadGameGfx` must select it.
3. **Register the tileset.** Add a `TileSet*` config block + an `idxTileSets`
   entry (id 8+); add a matching collision bitmap (`IdxColisTiles`) and, if new
   metatiles are needed, a new `Metatiles*` set + `idxMetatileSet` entry.
4. **Teach the tools.** `mgrender` reads gfx by label (offline, segment-agnostic)
   so it mostly works once the new labels exist; `mgmap`/the editor tileset
   dropdown lists 0–7 today and would extend to the new id.

## Phase B — DONE: extended tilesets loadable from reserved segments
Implemented as a self-contained **extended-tileset bank** + a tiny loader hook,
so room gfx-tileset ids **8–15** load their tiles/collision from the reserved
512KB space. Stock tilesets 0–7 are byte-for-byte untouched.

- **`BanksExtGfx.asm`** (segments 10h–12h; `REPT` reserve reduced 48→45) holds
  `idxTileSetsExt`, `TileSetExt*` configs, `IdxColisTilesExt`, `CollTilesExt*`,
  the `GfxExt*` tile data, and a `LoadExtDispatch` routine (mirrors the stock
  block + collision load, reusing the segment-0 helpers). Generated by
  `tools/genextgfx.py`. **Tileset 8 ships as an editable clone of Building**
  (GfxExt0/1 = the exact 135+40-tile Building span) with ~4KB + segments 11h/12h
  free for new tiles.
- **The hook**: there was no room in the full fixed code segment 0, so a ~21-byte
  **`ExtDivert`** lives in unused cartridge-header padding (#4014–#402F, no code
  shift) and replaces the post-crates `call SetBanks_7_8_9` in `LoadRoomTiles`.
  For gfx id<8 it's byte-equivalent (`jp SetBanks_7_8_9`); for id≥8 it routes
  through `SetBanks` (which maps segs 16/17/18 **and updates the BankIn shadow
  vars**) so that it `ret`s straight into `LoadExtDispatch`.
- **KEY GOTCHA (cost a black screen then garbled tiles):** Konami `SetBanks` is a
  tail-call (`pop af; ei; ret`) — you can't `call` it, and you MUST go through it
  (not raw `ld (#6000),a`) so the `BankIn60/80/A0` shadows stay correct, else an
  interrupt mid-load restores the wrong banks and gfx reads hit the wrong segment.
- **Tools**: `mgrender.resolve_tileset(gid)` reads `idxTileSetsExt`/`CollTilesExt`
  from `BanksExtGfx.asm` for gid≥8; the editor offers tileset 8 ("Building (ext)")
  and the tile pixel-editor can repaint its `GfxExt` tiles (your channel for new
  art). **Verified in openMSX**: a room set to tileset 8 renders identically to
  Building (loaded from the reserved segments); stock unaffected; build 0 errors /
  524288; selftest pass.

To ADD genuinely new tiles: set a room to tileset 8, repaint/extend the GfxExt
tiles with the editor's tile editor (room to grow in segments 10h–12h). Adding
more ext tilesets = append another `TileSetExt*`/`GfxExt*`/`CollTilesExt*` +
`idxTileSetsExt` entry (and reduce the reserve `REPT`).
